# Ecoswift Bank — Account Opening

**Phase 4A deliverable.** Account opening, ledger integration, and the full `AccountStatus` lifecycle — `services/account-service/src/modules/accounts`. See [`customer-onboarding.md`](customer-onboarding.md) for the profile/consent work this builds on, [`account-numbering.md`](account-numbering.md) for account number generation, and [`ledger-design.md`](ledger-design.md) for the double-entry model this phase is the first to actually post real customer-facing entries into.

---

## Account Types

Four `AccountType` catalog rows (`prisma/seed.ts` § `seedAccountTypes`), all opened through the same generic flow:

| Code | Name | Minimum Opening Balance |
|---|---|---|
| `CURRENT` | Current Account | 0 |
| `SAVINGS` | Savings Account | 0 |
| `FIXED_DEPOSIT` | Fixed Deposit Account | 100 |
| `BUSINESS` | Business Account | 0 |

`BUSINESS` is the brief's "future-ready" product — opened through the identical `POST /v1/accounts` flow as any other type, with no business-specific KYC, authorized-signatory review, or company-registration document flow built (see "What this phase did not build").

## Opening an Account

`POST /v1/accounts` — self-service only this phase. `customerId` is **always** derived server-side from the caller's own `Customer` record (`AccountService.open(userId, dto)` resolves it via `prisma.customer.findUnique({ where: { userId } })`) — never client-supplied, so there is no way to open an account against another customer's identity by passing a different id in the request body. Staff-assisted opening on behalf of a customer is not built this phase (see below).

Request:

```jsonc
{
  "accountTypeCode": "SAVINGS",   // CURRENT | SAVINGS | FIXED_DEPOSIT | BUSINESS
  "currencyCode": "USD",          // ISO 4217, must be an active seeded Currency
  "openingBalance": 0             // optional, default 0, must be >= the account type's minimum
}
```

Validation, in order: account type exists and `isActive`; currency exists and `status === 'ACTIVE'`; `openingBalance >= accountType.minimumOpeningBalance` (a `FIXED_DEPOSIT` request with less than 100 is rejected with `400` before anything is created).

Everything below happens inside one `prisma.$transaction`:

1. **`Account`** created, `status: 'PENDING_ACTIVATION'`.
2. **Ledger accounts** — `LedgerIntegrationService.createCustomerLedgerAccount()` creates the account's own `LedgerAccount` (category `LIABILITY` — a customer's balance is money the bank owes them) and a zeroed `AccountBalance` row. **Unconditional** — every opened account gets this, regardless of opening balance.
3. **Opening journal entry** — posted **only if `openingBalance > 0`**. See the next section for why this is conditional and what it means when it's skipped.
4. **`AccountOpened` event** published (`@ecoswift/event-bus`), **outside** the transaction, alongside an `AuditLog` entry and three notifications (Account Opened email, SMS confirmation if the customer has a phone on file, push notification) — deliberately not part of the financial transaction: a notification failure must never roll back money that has genuinely moved.

Account numbers are generated by `AccountNumberService` — see `account-numbering.md` for the full scheme.

## Opening Journal Entry

This is the one place in the brief where a literal reading and the actual database schema are in tension, and it's worth stating the resolution explicitly.

The brief asks to "Create opening journal entry" as part of account opening, but a hand-authored Phase 2B constraint —

```sql
ALTER TABLE "journal_lines" ADD CONSTRAINT "journal_lines_amount_positive" CHECK ("amount" > 0);
```

— makes a **zero-value** `JournalLine` impossible at the database level, full stop. A brand-new `SAVINGS`/`CURRENT`/`BUSINESS` account (minimum opening balance `0`) has no money attached to it yet — nothing has actually happened financially — so there is no honest non-zero pair of debit/credit lines to post. And the phase's own stop condition explicitly excludes **Deposits**, so there's no general-purpose "fund this account" mechanism to reach for either.

The resolution: **`openingBalance` is a property of account opening, not the Deposits feature.** It's the amount a customer chooses to fund the account with *at the moment of creation* — conceptually closer to "I'm opening this account with $500 in hand" than to "make a deposit into an existing account." Concretely:

- **`openingBalance == 0` (the default, and the only option for `CURRENT`/`SAVINGS`/`BUSINESS` unless the caller opts into more)** — no `JournalEntry` is created at all. The account's `LedgerAccount` and a `$0` `AccountBalance` still exist (step 2 above always runs) — the account has its place in the general ledger and is ready to receive real transactions in a future phase — but nothing is journaled, because nothing happened. This is the constraint working as intended, not a gap: a `$0` journal entry would be a lie about money having moved.
- **`openingBalance > 0` (required for `FIXED_DEPOSIT`, optional for the others)** — a real, balanced `JournalEntry` is posted: **debit** the bank's own `1000` "Cash and Bank Balances" ledger account, **credit** the new account's own `LedgerAccount`, both for `openingBalance`. This is standard double-entry treatment for funds entering the bank. It is deliberately narrow: no `Transaction` row is created, no deposit-processing endpoint exists, no ATM/mobile/wire deposit channel is touched — it's a one-time funding fact recorded at the exact moment an account comes into existence, not the general-purpose money-movement feature ("Deposits") the stop condition names as out of scope. A future Deposits phase adds the *ongoing* ability to fund an *existing* account; this phase only ever funds an account it is simultaneously creating.

`AccountBalance.availableBalance`/`currentBalance` are updated to `openingBalance` (from `0`) in the same step that posts the journal entry, and `lastJournalLineId` is set to the credit line — so `GET /v1/accounts/:id`'s `openingJournalNumber` field can trace a funded account's balance straight back to the entry that created it.

### Financial Period Auto-Provisioning

`JournalEntry.financialPeriodId` is required, and nothing before this phase ever posted an entry, so no `FinancialPeriod` had ever needed to exist. `LedgerIntegrationService.ensureCurrentFinancialPeriod()` finds (or creates, idempotently, calendar-month, `status: 'OPEN'`) the period covering today — a `LOCKED` period is refused outright (`InternalServerErrorException`), matching `FinancialPeriod`'s own doc comment ("LOCKED periods reject any new JournalEntry").

## `AccountStatus` Lifecycle

Six states (`PENDING_ACTIVATION`, `ACTIVE`, `FROZEN`, `DORMANT`, `CLOSED`, `RESTRICTED` — `RESTRICTED` is new this phase, additive migration). `AccountStatusService.transition()` enforces an explicit legal-transition table — nothing not listed is allowed:

```
PENDING_ACTIVATION -> ACTIVE, CLOSED
ACTIVE              -> FROZEN, DORMANT, RESTRICTED, CLOSED
FROZEN              -> ACTIVE, CLOSED
DORMANT             -> ACTIVE, CLOSED
RESTRICTED          -> ACTIVE, CLOSED
CLOSED              -> (terminal — no transitions out)
```

`CLOSED` has no outbound edges by design — real banks don't reopen a closed account, they open a new one. Every transition writes an `AuditLog` entry (`FREEZE` for `FROZEN`/`RESTRICTED`, `UNFREEZE` for a return to `ACTIVE`, `UPDATE` otherwise) and publishes `ACCOUNT_STATUS_CHANGED` (`@ecoswift/event-bus`, new this phase).

### Authorization per Transition

| Endpoint | Permission | Ownership |
|---|---|---|
| `POST /:id/activate` | `accounts:update` | Self, or staff holding `accounts:close` |
| `POST /:id/freeze` | `accounts:freeze` | Self, or staff holding `accounts:close` |
| `POST /:id/unfreeze` | `accounts:unfreeze` | Staff only — not granted to `CUSTOMER` |
| `POST /:id/close` | `accounts:close` | Staff only — not granted to `CUSTOMER` |
| `POST /:id/restrict` | `accounts:freeze` | Staff only (checked in-handler) |
| `POST /:id/unrestrict` | `accounts:unfreeze` | Staff only |
| `POST /:id/mark-dormant` | `accounts:update` | Staff only (checked in-handler) |
| `POST /:id/reactivate` | `accounts:update` | Self, or staff holding `accounts:close` |

This mirrors real banking practice deliberately: a customer can freeze their own account instantly (the same self-protective instinct as locking a card), but **un**-freezing, closing, restricting, and marking dormant all require staff — an attacker who has compromised a session cannot undo the legitimate account holder's own protective freeze. `accounts:close` is the highest-trust permission in the `accounts` resource, held only by staff roles in the catalog; it's reused here — not as its literal "close an account" meaning, but as a **staff marker** for the ownership bypass on the self-serviceable actions, the same convention `customer-onboarding.md` uses with `customers:delete`. `AccountsController`'s own doc comment names this convention explicitly.

## Ledger Integration Summary

| Step | Table(s) | Always, or conditional? |
|---|---|---|
| Create ledger account | `LedgerAccount` (category `LIABILITY`), `AccountBalance` (zeroed) | Always |
| Post opening journal entry | `JournalEntry`, 2× `JournalLine` (debit `1000` Cash, credit the new `LedgerAccount`) | Only if `openingBalance > 0` |
| Publish `AccountOpened` | `@ecoswift/event-bus` | Always |
| Write audit log | `AuditLog` (hash-chained, same global chain Phase 3B built) | Always |
| Generate internal reference | The `journalNumber` (`JE` + 9 digits) **is** the internal reference for the funding event — see `account-numbering.md` for the account number's own scheme | Only when a journal entry exists |

## Notifications

Sent from `open()`, outside the ledger transaction: **Account Opened** email (new template, `prisma/templates/emails/account-opened.html`), **SMS confirmation** (only if the customer has a verified phone on file — silently skipped otherwise, not an error), and a **push notification** (new `ACCOUNT_OPENED_PUSH` template — the first phase to need `@ecoswift/queue`'s `PUSH_QUEUE`, since no prior feature sent one). **Welcome Email** is deliberately *not* re-sent here — it already fires once, at registration (Phase 3A) — sending it again at account-opening would misrepresent "welcome to the bank" as "welcome to this specific account."

## Live Verification

Every claim above was exercised against a real, running `account-service` (real Postgres/Redis) during this phase, not just unit-tested:

- A `$0` `SAVINGS` account opening produced **no** `JournalEntry` row; its `LedgerAccount`/`AccountBalance` existed regardless.
- A `FIXED_DEPOSIT` opened with `openingBalance: 500` produced a real, balanced `JournalEntry` — queried directly from Postgres, its two `JournalLine`s were `DEBIT 500.0000` against `1000` ("Cash and Bank Balances") and `CREDIT 500.0000` against the new account's own `LedgerAccount`.
- A `FIXED_DEPOSIT` request with `openingBalance: 10` (below the 100 minimum) was rejected `400` before any row was written.
- Every generated account number passed its own Luhn check digit.
- Self-service `activate` and `freeze` succeeded for the owning customer; `unfreeze` and `close` correctly `403`'d for that same non-staff customer.
- `AuditLog` and `Notification` rows were confirmed written for every action above.

## What this phase did not build

- **Staff-assisted account opening on behalf of a customer.** Every account-opening request derives its `customerId` from the caller's own identity; there is no `POST /v1/accounts` variant that lets an `OPERATIONS_OFFICER` open an account for someone else. A natural next step — likely an explicit `customerId` field on the request, gated by a staff-only bypass on `accounts:create`, the same ownership pattern already used for status transitions.
- **Enforcing consent/profile-completion as a precondition of account opening.** `ConsentService.hasAcceptedMandatoryConsents()` exists (`customer-onboarding.md`) but `AccountService.open()` does not call it. A production system would very likely gate account opening on it; this phase builds both pieces correctly but does not wire them together, to keep this phase's scope to what the brief explicitly asked for.
- **Transfers, Deposits, Withdrawals, Loans, Savings engine, Receipt generation, Dashboard UI** — the phase's explicit stop condition. No `Transaction` row is ever created by anything in this phase; the only money movement possible is the one-time opening-balance journal entry described above, which is intentionally not built as a reusable deposit primitive.
- **Business-specific KYC for the `BUSINESS` account type** — it opens through the identical generic flow as every other product; company registration documents, authorized-signatory verification, and business-tier limits are unbuilt.
- **Batch dormancy detection.** `mark-dormant` exists as a manual staff action; nothing in this phase watches for actual account inactivity and calls it automatically.
